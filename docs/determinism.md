# Cross-architecture determinism

AC-18 and AC-25 require the same golden fixtures, and the same effective Config
and Seed, to pass on native amd64 and native arm64. Specification section 13
and premise P45 are explicit that emulation does not prove that. This note
records the strongest evidence available on a machine with no git remote, and
the limit of that evidence.

## What was measured

- Date: 2026-09-27
- CPU: Apple M4 Pro (native arm64). Rosetta 2 is installed: `arch -x86_64 /usr/bin/true` succeeded.
- System: Darwin arm64
- Go: `go1.26.4`
- amd64 test binary: `GOARCH=amd64 go test -c` produced `Mach-O 64-bit executable x86_64`. macOS ran that binary under Rosetta 2.

Commands and results:

```
GOARCH=amd64 go test -count=1 ./...
```

Exit 0. 353 tests passed across 8 packages.

```
GOARCH=amd64 go test -count=1 -run '^TestFrozenGoldenLayouts$' .
```

Exit 0. The x86_64 test binary, run with `-test.v`, passed
`TestFrozenGoldenLayouts` and the five frozen cases:
`shapes_bounds_gap_catalog`, `prim_tie_break_and_weights`, `winding_bfs`,
`corridors_share_cell`, `poisson_rejection_and_density`.

The eight-configuration Layout snapshot (Rooms, Corridors, Doors, and every
non-empty Grid cell) was generated by the temporary test and then deleted.
Both architectures wrote 12943 lines. SHA-256 of both files:

```
c8e41ac7b59a253316e45c0b691723fa7a3a574e74c99478e769a7cef5062650
```

`cmp` reported the two files identical. That is the reference hash. The native
arm64 run is the control; the amd64 run is the cross-architecture comparison.

a target: the Makefile refuses a shortcut that rewrites frozen fixtures

## What this proves

The float paths that would diverge across architectures are compiled
differently for amd64. Go may fuse `a*b+c` into a single FMA on arm64 and must
not on amd64. The amd64 binary executed here uses the amd64 instruction
sequence, under Rosetta, and it matches the native arm64 snapshot and the
committed golden files bit for bit. A contraction bug in those expressions
would have shown up as a golden or snapshot mismatch.

## What this does not prove

It does not prove AC-18 or AC-25. Rosetta 2 is emulation. Section 13 and P45
rule emulation out as proof of architecture determinism. The CI job
`determinism` in `.github/workflows/ci.yml` is the check that would count: the
same `go test -count=1 ./...` on native `ubuntu-latest` (amd64) and native
`ubuntu-24.04-arm`. This repository has no git remote, so that job has never
been scheduled. Nothing here shows that GitHub's arm64 runner accepts the job.

Premise P44 also names ppc64 and s390x as architectures that can contract FMA.
AC-18 and AC-25 do not require those machines, and this run did not cover them.

## Source audit

No violation turned up. Nothing in the generation path was changed.

### FMA contraction

Every product and sum that affects a candidate, distance, weight, priority, or
tie-break in `poisson.go`, `prim.go`, `placement.go`, and `roles.go` is already
in separate statements. The lines that both multiply and add are integer
indexing or an integer capacity, not binary64:

| Location | Expression | Why it is not an FMA hazard |
| --- | --- | --- |
| `poisson.go` acceleration index | `y*grid.columns + x` | `int64` cell index |
| `roles.go` backbone pair flags | `fromIndex*roomCount + toIndex` and the swapped pair | `int` index |
| `roles.go` shortcut scan | `firstIndex*roomCount + secondIndex` | `int` index |
| `roles.go` candidate capacity | `roomCount * (roomCount - …) / …` | `int` slice capacity; not a weight |

Float steps that the specification calls out are split, with an explicit
`float64` intermediate where a product is rounded before it is added:

- Annulus sample (`poisson.go`): `uniform01()*width`, then a separate subtraction of the half-width; each square is its own statement; the two squares are added only after that.
- Prim center (`prim.go`): span subtraction, division by two, and the add onto the origin are three statements per axis.
- Squared center distance (`prim.go`, used by Prim and by role distance): each square is stored, then the squares are added.
- Role path length (`roles.go`): the running distance is loaded, then the neighbor weight is added in the next statement.
- Anchor separation (`placement.go`): `dx` and `dy` squares are `int64`; only the required distance is squared, in a multiply with no add.

`math.Floor` and `math.Ceil` appear on the acceleration grid and on anchor
quantization. They are not fused multiply-adds. The same scan of `routing.go`,
`room_shape.go`, `generator.go`, and `rng.go` found no binary64 `a*b+c`.

### Trigonometry

The generation path does not call `sin`, `cos`, or any other libm
trigonometry. `math.Sqrt` is used twice: the Poisson acceleration cell size
(`minimumDistance / math.Sqrt(bridsonDimensions)` in `poisson.go`, with
`bridsonDimensions` equal to 2) and the Euclidean edge
weight for thematic distance (`roles.go`). Premise P31 allows `math.Sqrt`
because IEEE-754 requires it to be correctly rounded. Distance checks that
only need an order compare squares and do not call it.

### Map iteration

No map is iterated on the generation path. Membership sets (`seen` in
`generator.go`, the overlap oracle in `placement.go`) are only probed by key.
`for range` walks slices, or the fixed array `roomGeometrySampler.starts`.
Bucket order in the Poisson acceleration grid is nested integer loops, not a
map. Premise P43's deterministic BFS does not range over a map.

## CI job

`.github/workflows/ci.yml` job `determinism` already uses a matrix of native
labels, `ubuntu-latest` and `ubuntu-24.04-arm`. It does not install QEMU and
does not use `docker buildx --platform`. `fail-fast` is false, so one
architecture cannot cancel the other. There is no `if` and no
`continue-on-error`, so the arm64 leg is not skipped when another job fails.

GitHub's runner docs say a job whose labels match no online runner stays
queued and fails only after the 24-hour queue limit. `timeout-minutes` limits
execution, not that wait. Workflow syntax cannot turn "no `ubuntu-24.04-arm`
runner" into an immediate failure, and this file does not pretend otherwise.

Once a machine does accept the job, a green suite on the wrong machine would
be a false proof. The job's first step now fails, with an `::error::`
annotation, before `go test` if:

- `uname -m` is not `x86_64` on `ubuntu-latest` or not `aarch64` on `ubuntu-24.04-arm`, or
- `/proc/self/maps` shows a QEMU user-mode interpreter (`qemu-`).

The suite command is unchanged: `go test -count=1 ./...`.
